# Cell-border placement and 394-case assessment

After the Unicode ZIP-path and assignment-field changes, the complete 394-case comparison (`final-394-result.json`) recorded **190 passed, 186 failed, and 18 blocked**. The pinned Wordcraft source and EdgeDoc build fingerprints were checked both before and after the run. This is a baseline before the subsequent cell-border change, not a claim of full parity. Failures and blocks include unsupported layout and objects, missing matching font data, reference-adapter limitations, malformed or encrypted inputs, and visual or pagination differences.

The cell-border change centers the vertical stroke on the cell grid line and extends horizontal strokes across their adjoining corners, following the Wordcraft rendering of explicit cell borders. In the focused four-cell example, the comparison changed from a mean common-ink color error of 0.1006 to 0.0441, below the configured 0.05 threshold; unmatched ink is zero and glyph positions match. The `cell-border-focused-result.json` and `cell-border-image-inspection/` record the comparison and the paired images inspected. The remaining color difference means this result is threshold parity for that example, not pixel identity.

The first version regressed the real `poi-31-table-indent` case. Wordcraft's compatibility-mode code showed that modern, start-aligned tables with an explicit first-cell border place their grid half a border width inside the margin. Applying that offset and extending each horizontal edge only where its vertical border is visible fixes the regression. The final `cell-border-191-result.json` records **191/191 passes**, including the original 190 passing cases and the new border example. Workspace tests, strict clippy and formatting checks passed, as did browser checks (18/18 interactions and 134/134 corpus checks across 33 documents).
